# Ревизия кода: Messenger / IMessenger

Дата: 29 мая 2026

Краткое описание
- Проведена статическая ревизия файлов интерфейса и реализации механизма сообщений в папке Mediator.
- Найдены ошибки компиляции, потенциальные проблемы по потокобезопасности и предложения по улучшению.

Найденные проблемы и предложения

- Компиляционные ошибки
  - [MathCore/Mediator/Messenger.cs](MathCore/Mediator/Messenger.cs): использование литерала `[]` при создании списка обработчиков (в `GetOrAdd(Address ?? "", _ => [])`) некорректно — нужно создать `new List<Delegate>()`.
  - [MathCore/Mediator/IMessenger.cs](MathCore/Mediator/IMessenger.cs): в интерфейсе указаны модификаторы доступа `public` у членов интерфейса. В объявлении интерфейса надо убрать `public` (члены интерфейса по умолчанию публичные). Это вызывает ошибку компиляции.

- Нереализованные методы
  - `Messenger.RemoveHandler<T>(EventHandler<T> Handler)` бросает `NotImplementedException` — требуется реализация удаления обработчика (по всем адресам или конкретному адресу, в зависимости от семантики).

- Потенциальные улучшения и замечания по безопасности/надёжности
  - Текущее хранение `List<Delegate>` внутри `ConcurrentDictionary` требует явной синхронизации (в коде используется `lock (address_handlers)`), но при удалении последнего обработчика стоит очищать/удалять пустой список и удалять пустую запись по типу сообщения, чтобы избегать утечек памяти.
  - Приведение `address_handlers.Cast<EventHandler<T>>()` безопасно при условии, что в список попадают только `EventHandler<T>`, но общая структура хранит `Delegate` — рекомендую ограничить область видимости типов или хранить `List<EventHandler<object>>`/обёртки, чтобы избежать неявных ошибок приведения.
  - В `SendAsync` все обработчики выполняются последовательно в контексте `TaskScheduler`. Рассмотреть:
    - выполнение обработчиков параллельно (если это приемлемо),
    - обработку исключений каждого обработчика отдельно (чтобы один упавший обработчик не прерывал выполнение остальных),
    - время ожидания/таймаут для каждого обработчика при необходимости.
  - Рекомендуется добавить логирование ошибок обработчиков и метрик (кол-во зарегистрированных обработчиков, время выполнения и т.д.).

- Стиль и API
  - Полезно реализовать возвращаемые значения у `AddHandle` (или предоставить метод `HasHandlers<T>(string? address)`), чтобы клиент мог проверить регистрацию.
  - Рассмотреть API для приоритизации/порядка вызова обработчиков при необходимости.

Рекомендуемые точные правки (псевдо‑патчи)

- Исправить создание списка:

  В `Messenger.AddHandle<T>` заменить `handlers.GetOrAdd(Address ?? "", _ => [])` на `handlers.GetOrAdd(Address ?? "", _ => new List<Delegate>())`.

- Убрать `public` в интерфейсе:

  В `IMessenger.cs` заменить сигнатуры вида `public void AddHandle<T>(...)` на `void AddHandle<T>(...)` для всех членов интерфейса.

- Реализовать `RemoveHandler<T>(EventHandler<T> Handler)` примерно так:

  - Перебирать внутренний словарь по типу сообщений и адресам,
  - Удалять указанный обработчик из списка с `lock`,
  - Если список становится пустым — удалить запись адреса; если у типа сообщений не осталось адресов — удалить тип из `_Handlers`.
