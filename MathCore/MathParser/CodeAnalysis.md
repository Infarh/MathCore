# Анализ кода парсера математических выражений

## 1. Общая архитектура и назначение

- Подсистема `MathCore.MathParser` реализует разбор строкового математического выражения в собственное дерево вычислений (`ExpressionTree`), а затем компиляцию в `System.Linq.Expressions` и делегаты.
- Основные участники: `ExpressionParser`, `MathExpression`, `Term`/`BlockTerm`/`NumberTerm`/`StringTerm`/`CharTerm`/`FunctionTerm`/`FunctionalTerm`, дерево `ExpressionTree` и иерархия узлов `ExpressionTreeNode` (`OperatorNode`, `ComputedNode`, `FunctionNode`, `VariableValueNode`, …).
- Архитектура исторически развивалась и содержит как сильные стороны (богатая модель, поддержка функционалов/дифференцирования), так и технический долг (сложный код комбинирования узлов, низкий уровень инкапсуляции, ручное управление приоритетами операторов).

## 2. Функциональная корректность и потенциальные ошибки

### 2.1. `ExpressionParser.ProcessNewNode`

```csharp
protected virtual void ProcessNewNode(ref ExpressionTreeNode NewNode)
{
    switch (NewNode)
    {
        case CharNode char_node:
        {
            switch (char_node.Value)
            {
                case '.' when NewNode.Parent is CharNode { Value: '.' }:
                    var value_node = NewNode[n => n.Parent].Last(n => n is not OperatorNode || n.Left is null);
                    (NewNode["./."] ?? throw new InvalidOperationException("NewNode/. is null")).Right = null;
                    var parent        = value_node.Parent;
                    var interval_node = new IntervalNode(value_node);
                    if (parent != null) parent.Right = interval_node;
                    NewNode = interval_node;
                    break;
            }
            break;
        }
        case OperatorNode:
            break;
    }
}
```

Проблемы:
- Хрупкая логика поиска `value_node` по цепочке родителей и индексу `"./."`. При нетипичных структурах дерева возможны:
  - `InvalidOperationException` при отсутствии узлов, удовлетворяющих `Last(...)`.
  - `NullReferenceException` при неожиданных комбинациях, если `NewNode["./."]` возвращает `null` (сейчас перехватывается только как `InvalidOperationException`).
- Семантика преобразования `..` в `IntervalNode` не документирована, трудно тестируема и расширяема.

Предложения:
- Выделить отдельный хорошо задокументированный метод/класс для распознавания интервалов/диапазонов.
- Заменить магические пути вида `"./."` на строго типизированные обходы дерева.
- Добавить целевые юнит‑тесты для типовых и граничных случаев использования `..` (несколько точек, отсутствие левого/правого операнда и т.п.).

### 2.2. `ExpressionParser.Combine`

Код `Combine` очень сложен, с высокой цикломатической сложностью и большим числом ветвлений, опирается на `Priority` операторов и взаимное положение узлов.

Проблемы:
- Поддержка приоритетов операторов реализована вручную через обход родителей/правых поддеревьев.
- Есть явно незавершённый код:

```csharp
else // если оператор в корне дерева имеет меньший приоритет, чем приоритет текущего оператора
    //  то вставить текущий оператор в правое поддерево родителя предыдущего оператора
    throw new NotImplementedException("!!!");
```

Это потенциальный источник `NotImplementedException` для некоторых комбинаций операторов/приоритетов (скорее всего, редко встречающихся выражений, но формально — дефект).

- Много мест, где косвенно предполагается, что `Parent`, `Left`, `Right` не равны `null`, без явных проверок; любые будущие изменения структуры узлов легко сломают эту логику.
- Правила неявного умножения (константа/скобки рядом) зашиты непосредственно в `Combine`, что усложняет сопровождение.

Предложения (в порядке возрастания изменений):
- Краткосрочно: добавить юнит‑тесты/property‑based тесты на разные комбинации операторов и убедиться, что ветка `NotImplementedException` недостижима, либо реализовать корректное поведение (например, классический алгоритм сортировочной станции или построение AST по приоритетам).
- Долгосрочно: переписать построение дерева из последовательности `Term[]` на более классический алгоритм:
  - Преобразование в ОПН (shunting-yard) с учётом приоритетов и ассоциативности.
  - Построение дерева из ОПН.
  - В этом случае метод `Combine` станет сильно проще или вообще исчезнет, а логика приоритетов — декларативной.

### 2.3. `ExpressionParser.ProcessVariables`

```csharp
var tree_vars = Expression.Tree.Root.GetVariables().ToArray();
Expression.Variable
   .Where(v => !tree_vars.Contains(v))
   .ToArray()
   .Foreach(v => Expression.Variable.Remove(v));
```

Проблемы:
- Сравнение переменных по ссылке (`Contains(v)` с объектами `ExpressionVariable`), а не по имени. Это может оставить в коллекции переменные с тем же именем, но другими экземплярами, либо, наоборот, удалить корректные, если в дереве был создан новый объект переменной.
- Потенциально неочевидный порядок обработки: сначала фильтрация по ссылкам, потом перенос констант. Никак не описано ожидаемое поведение при конфликтах имён.

Предложения:
- Сравнивать переменные по имени: `var tree_var_names = new HashSet<string>(tree_vars.Select(v => v.Name));`.
- Явно задокументировать инварианты: каждая переменная уникальна по имени, коллекции `Variables`/`Constants` не должны содержать дубликатов.

### 2.4. `ExpressionParser.ProcessFunctions`

- Логика разрешения функций захардкожена в большом `switch`, с дублированием имён (разные регистры) и множеством `case`.
- Поддерживаются только функции с 1 или 2 аргументами, без явной диагностики для других количеств (ошибка появляется только после неудачного поиска делегата).
- Потенциальная путаница между `ATAN` (1 аргумент) и `ATAN2` (2 аргумента) — сейчас различение сделано по `Arguments.Count`, но при ошибках в разборе можно получить неожиданные делегаты.

Предложения:
- Вынести словарь стандартных функций вида `Dictionary<(string name,int argCount), Delegate>` с нормализованным регистром ключа, например `name.ToLowerInvariant()`.
- Чётко диагностировать неподдерживаемые комбинации `name/argCount` до вызова события `FindFunction`.
- В `FindFunction` оставить возможность переопределения/расширения.

### 2.5. `ExpressionTreeNode` индексаторы и обходы

```csharp
public IEnumerable<ExpressionTreeNode> this[ChildNodeSelector ChildSelector]
{
    get
    {
        yield return this;
        for (var node = ChildSelector(Left!, Right!); node != null; node = ChildSelector(node.Left!, node.Right!))
            yield return node;
    }
}
```

Проблемы:
- Использование `!` без проверок: при отсутствии дочерних узлов (что допустимо) будет `NullReferenceException` при первом вызове `ChildSelector(Left!, Right!)`.
- Этот индексатор используется, например, в `LastLeftChild`/`LastRightChild`; на пустом дереве они могут падать или вести себя неожиданно.

Предложения:
- Явно обрабатывать случай отсутствия дочерних узлов: не вызывать `ChildSelector`, если `Left == null && Right == null`.
- Для `LastLeftChild`/`LastRightChild` добавить проверку на пустое дерево/листовой узел.

### 2.6. `ExpressionTreeNode.GetVariables/GetFunctions/GetFunctionals`

```csharp
IEnumerable<ExpressionVariable>? variables = null;
if (_Left != null)
    variables = _Left.GetVariables();
return _Right != null
    ? variables.AppendLast(_Right.GetVariables()).Distinct()
    : [];
```

Проблемы:
- Если `_Left == null`, `variables` остаётся `null`, и дальнейший вызов `variables.AppendLast(...)` приведёт к `NullReferenceException` (зависит от реализации `AppendLast`).
- Потенциально дорогая операция `Distinct()` на каждом узле дерева.

Предложения:
- Использовать безопасную инициализацию: `var variables = Enumerable.Empty<ExpressionVariable>();` и затем конкатенацию.
- При необходимости оптимизировать сбор переменных/функций за счёт кеширования на уровне `ExpressionTree` (по профилированию).

### 2.7. `ExpressionTreeNode.Remove` и `ExpressionTree.Remove`

Обе реализации содержат схожую, но не идентичную логику удаления узла и подстыковки поддеревьев, что повышает риск расхождений.

Проблемы:
- Дублирование алгоритма удаления (в `ExpressionTreeNode.Remove` и `ExpressionTree.Remove`).
- Сложная манипуляция ссылками родителей/детей; любые будущие изменения легко внесут баги (утечки узлов, некорректные деревья).

Предложения:
- Выбрать один «источник истины» для удаления (например, реализация на уровне дерева) и использовать его в другом месте, либо вынести общий алгоритм в утилитарный метод.
- Покрыть удаление юнит‑тестами: удаление корня, листа, узла с одним/двумя детьми, левый/правый подузел.

## 3. Дизайн, расширяемость и читаемость

### 3.1. Смешение этапов парсинга

Текущий конвейер:
- `BlockTerm.GetTerms` выполняет токенизацию строки + разбор блоков/функций/функционалов, создавая иерархию `Term`.
- `ExpressionParser.GetRoot` последовательно для каждого `Term` строит поддеревья и "комбинирует" их в общее дерево через `Combine`.

Проблемы:
- Этапы лексического и синтаксического анализа переплетены:
  - `BlockTerm` частично знает синтаксис (`FunctionTerm`, `FunctionalTerm`, блоки `{}`),
  - `ExpressionParser` через `Combine` фактически реализует синтаксический анализ выражений с приоритетами.
- Расширять синтаксис (новые операторы, унарные/постфиксные операторы, новые виды скобок) сложно и рискованно.

Предложения:
- Долгосрочно разделить:
  - Лексер (`string` → список токенов/термов без построения дерева).
  - Парсер (`токены` → AST, с ясной грамматикой и таблицей приоритетов).
  - Преобразователь AST → `ExpressionTreeNode`.

### 3.2. Использование событий как расширяемости

`ExpressionParser` даёт несколько событий (`NewNodeAdded`, `StringPreprocessing`, `FindFunction`, `VariableProcessing`). Это гибко, но:
- Сильно связывает жизненный цикл парсинга с внешними подписчиками, затрудняет тестирование (невидимые побочные эффекты).
- Смешивает ответственность: парсер и обработка доменной логики переменных/функций.

Предложения:
- Для больших сценариев заменить события на явные расширяемые контракты (например, `IFunctionResolver`, `IVariableResolver`, передаваемые в конструктор/метод `Parse`).
- Сохранить события для обратной совместимости, но сделать их thin‑оберткой над сервисами.

### 3.3. Именование и единообразие

- Класс `subtractionOperatorNode` не соответствует общему PascalCase‑стилю.
- Встречаются Unicode‑символы для операторов и функционалов (`×`, `·`, `Σ`, `∫`, `√` и т.п.), что полезно, но требует чёткого документирования и тестирования (особенно в кроссплатформенной среде и разных редакторах).

Предложения:
- Привести имена типов к единообразию (PascalCase) с сохранением бинарной совместимости через `Obsolete` или `type-forward` только при необходимости.
- Задокументировать поддерживаемый синтаксис, включая Unicode‑операторы, в README/документации.

## 4. Производительность

### 4.1. Создание временных коллекций при разборе

Примеры:
- `ExpressionParser.ProcessVariables`: несколько `.ToArray()` подряд.
- `BlockTerm.GetTerms`: строковая конкатенация для имени `result += Str[i++]`, постоянные `Substring`/`GetBracketText`.

Предложения:
- Заменить конкатенацию строк в циклах на `StringBuilder` или работу с индексами/срезами.
- Избегать лишних `ToArray()` там, где можно итерироваться по коллекции напрямую.
- При необходимости профилировать на типичных выражениях (длинные формулы, вложенные функции).

### 4.2. Компиляция выражений

В `MathExpression.Compile*` компиляция производится каждый раз при вызове.

Предложения:
- Добавить возможность кеширования скомпилированных делегатов внутри `MathExpression` (опционально), либо явный API `BuildCompiled()`.
- Обеспечить сброс кеша при изменении дерева/переменных структуры.

## 5. Тестирование и надёжность

В проекте уже есть подробные тесты (`ParseEquationsTests`, `ExpressionParserTests` и др.), которые проверяют структуру дерева на сложных выражениях.

Рекомендованные дополнительные тесты:
- Пограничные случаи синтаксиса:
  - Пустые выражения, только константы, только переменные.
  - Несбалансированные скобки, неожиданные символы.
  - Некорректные/неподдерживаемые функции и функционалы.
- Систематические проверки приоритетов операторов:
  - Выражения вида `a+b*c`, `a*b^c`, `-a^b`, комбинированные логические выражения.
- Тесты на `ExpressionTreeNode.Remove`/`ExpressionTree.Remove` и `Swap`.
- Тесты на корректность обработки `..` → `IntervalNode`.
- Property‑based тесты (например, на основе генерации случайных деревьев и сравнении результата `Compute` до/после различных трансформаций `Swap/Remove`).

## 6. Возможности модернизации

### 6.1. Грамматика и AST

- Ввести явную модель AST (простые DTO‑классы без ссылок на вычислительные `ExpressionTreeNode`), описывающую грамматику: литерал, переменная, унарный/бинарный оператор, вызов функции, функционал, условный оператор, интервал и т.п.
- Разделить парсер на два этапа: `string → AST` и `AST → ExpressionTreeNode`.
- Это упростит:
  - Добавление новых элементов языка.
  - Оптимизации (упрощения выражений, предвычисление констант).
  - Валидацию и понятные сообщения об ошибках парсинга.

### 6.2. Оптимизации дерева и компиляции

- Реализовать отдельный шаг оптимизации дерева (constant folding, устранение мёртвых веток в тернарных/логических выражениях, нормализация вида).
- Добавить API для анализа выражения перед компиляцией: список переменных с типами, список функций и функционалов, оценка сложности.

### 6.3. Улучшение API `ExpressionParser`

- Сделать `ExpressionParser` stateless, без изменяемых полей (кроме, возможно, таблицы констант/функций), чтобы один экземпляр можно было безопасно использовать из разных потоков.
- Конфигурацию (разделители, набор констант, функции) вынести в отдельный `ExpressionParserOptions` и поддерживать неизменяемость.

## 7. Предлагаемая дорожная карта рефакторинга

### Этап 1. Безопасность и исправление явных дефектов

1. Закрыть `NotImplementedException` в `Combine` или доказать недостижимость и заменить на корректную ветку.
2. Исправить `GetVariables`/`GetFunctions`/`GetFunctionals` на безопасную инициализацию коллекций.
3. Упростить и обезопасить индексаторы в `ExpressionTreeNode` (`ChildNodeSelector`, `NodeSelector`).
4. Уточнить логику `ProcessVariables` (сравнение по имени, тесты).
5. Добавить юнит‑тесты на `ProcessNewNode`/`IntervalNode` и операции с деревом (`Remove`, `Swap`).

### Этап 2. Улучшение читаемости и структуры

6. Локальный рефакторинг `Combine` без изменения внешнего поведения:
   - Разбить на несколько приватных методов (обработка операторов, неявное умножение и т.п.).
   - Уменьшить вложенность условий.
7. Вынести таблицу стандартных функций в отдельную структуру (словарь), заменить цепочки `switch` на поиск по ключу.
8. Привести имена типов операторов к единообразию (`SubtractionOperatorNode` и т.п.).

### Этап 3. Архитектурные изменения (по мере необходимости)

9. Проектирование и реализация явной AST‑модели грамматики.
10. Реализация нового парсера `string → AST` (например, на основе shunting‑yard), при сохранении текущего публичного API.
11. Реализация трансформации `AST → ExpressionTreeNode` и миграция существующих тестов.

### Этап 4. Оптимизация и расширение

12. Введение шага оптимизации дерева (constant folding, упрощения).
13. Кеширование скомпилированных делегатов в `MathExpression` (опционально с возможностью инвалидации).
14. Добавление расширенных возможностей: пользовательские типы, векторы/матрицы, функции большего числа аргументов.

---

Этот документ описывает текущие основные проблемы, точки риска и направления развития механизма парсинга и компиляции математических выражений. При выполнении рефакторинга рекомендуется двигаться итеративно, начиная с этапа 1 и постоянно поддерживая зелёный набор существующих тестов.
